# 规则引擎 + 云端大模型：分镜规划实验 v0.1

日期：2026-11-04

## 目标

不让模型直接生成整份分镜 Markdown，而是：

```text
标准剧本 → 规则拆场和源块 → 云端输出镜头计划 JSON → 本地编译 → 本地质检
```

模型只做镜头判断；台词、编号、时长、格式和交付文件都由确定性代码处理。

## 输入与输出契约

输入：

- 集名、场景标题、人物行；
- 按顺序编号的动作/台词源块；
- 下一场的前几行作为衔接提示。

模型输出：

- shot 级 `cast` 和 `props`；
- shot 时长与开场空间状态；
- Clip 时长、景别、运镜、可见动作；
- 每个 Clip 引用的 `sourceBlockIds`。

模型不返回台词正文。编译器根据 `sourceBlockIds` 从源剧本回填台词，保证一字不改。

## 实测结果

样本：

- `tests/fixtures/final-script.txt`
- 第 1 集 `1-1 Village 外 未注明`
- 62 个源块

结果：

- 模型状态：`completed`
- 32 shot / 50 Clip
- 62/62 源块全部覆盖，无重复引用
- shot / Clip 时长全部合法，且 Clip 加总等于 shot 时长
- shot 级人物和道具全部匹配源场景
- 现有引擎内容质检：0 问题
- 模型耗时：约 131 秒
- Token：输入 5,362；输出 27,254；其中思考 21,502

原始模型输出已保存为：

- `tests/fixtures/scene-plan-1-1.raw.json`

## 观察

有效：

- 对话原文没有漂移，因为模型只引用块号。
- 镜头数量和时长由本地最终校验，不依赖模型口述“已完成”。
- 每个 shot 能单独限制人物和道具，避免整场人物/道具污染所有镜头。
- JSON 计划明显短于最终 Markdown，适合分批、重试和逐镜审计。

仍需处理：

- 一次 62 个源块的单场调用仍需约 2 分钟，思考 token 占大头。
- 第一次在 24,000 输出上限时曾因思考耗尽而截断 JSON；改为 64,000 并缩短下一场摘要后完成。
- 当前只有纯规则结构校验，还没有自动二次修正。
- 尚未与现有整稿提示词做人工质量 A/B；下一阶段应比较镜头节奏、动作闭合和导演意图。

## 两套规则对照（同场 62 源块）

| 指标 | 严格 3 Clip | 灵活 6 Clip |
| --- | ---: | ---: |
| Clip 时长下限 | 4 秒 | 2 秒 |
| shot 数 | 8 | 12 |
| Clip 数 | 17 | 33 |
| 实际最大 Clip 数 | 3 | 4 |
| 分镜总时长 | 82 秒 | 96 秒 |
| 平均 shot | 10.3 秒 | 8.0 秒 |
| 中景及以上占比 | 11.8% | 24.2% |
| 不同运镜描述 | 4 种 | 20 种 |
| 内容预算过载 Clip | 7 | 13 |
| 模型耗时 | 92 秒 | 110 秒 |
| 总 token | 22,125 | 27,877 |

解释：

- 严格配置把更多动作、反应和台词塞进少数长 Clip，格式合法但存在明显的“5 秒装 10 秒内容”问题。
- 灵活配置的镜头节奏和运镜明显更丰富，6 Clip 上限没有导致无节制切碎；本次实际最多只用了 4 个 Clip。
- 两套配置都被本地内容预算检查抓出过载 Clip，说明“放开 Clip 数”本身不能解决超长问题。真正有效的是先限制每个规划单元承载的源内容量，再让模型规划。
- 运镜多样性增加可能是优点，也可能造成过碎，必须结合人工观感判断，不能只看数量。

## 分块规划与本地纠错

把同一场按约 20 秒内容预算拆成 6 个连续规划单元后，逐段调用云端模型：

- 第一轮共产生 16 shot / 46 Clip；
- 内容过载从整场一次规划的 13 个降到 1 个；
- 模型仍有少量漂移：一个“大魔导师”短名未匹配登记名，一个 shot 只有 4 秒；
- 本地确定性修复做了 35 处调整：补足短 Clip、修正 shot 总时长、统一人物短名；
- 修复后：16 shot / 46 Clip，全部结构规则、现有内容 QC 均为 0 问题。
- 分块调用共发生 10 次模型请求（含 4 次修复），累计 77,459 token，串行耗时约 318 秒。分段显著降低单次压力，但串行成本偏高，正式版本需要并行执行互不依赖的规划单元。

但总时长从模型初稿的 123 秒，修正内容预算后变成 145 秒，超过了单集 75–105 秒窗口。这说明这场原始戏本身就需要更早地拆开，不能靠压缩镜头硬塞进一集。规则引擎能发现并修复局部格式问题，但不应该凭空删除内容来满足时长。

时长裁决器随后在完整 shot 边界上重新装箱，得到：

- 第 1 集：76 秒，7 shot，窗口内；
- 第 2 集：69 秒，9 shot，低于下限 6 秒；
- 不拆分任何 shot，不删除任何源块。

这里不会伪造“通过”：第 2 集会被标成短集，建议与相邻场景或下集内容合并，或由用户明确接受。裁决器只给出可追溯的切点，成片钩子和最终剪辑点仍由制作人员判断。

## 下一步

1. 把长场按源块切为约 15–20 块的规划单元，同时维护跨单元的人物、道具和结尾状态账本。
2. 模型计划不合格时，只提交错误位置和原计划给模型做一次定点修复。
3. 用三场戏做 A/B：
   - 现有整稿提示词；
   - 规则引擎 + 云端 JSON 规划。
4. 确认质量后再接进流程三，不先替换现有链路。
