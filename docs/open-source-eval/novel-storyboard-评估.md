## 二、它是什么

三层结构：

```
段（segment，一次生成，≤15 秒）
  └─ 镜（cut，段内一次剪切，2–5 秒）
       └─ 分镜图（每个 cut 一张关键帧）
```

**核心机制：镜头认领节拍。** 每个 cut 声明它覆盖剧本某场的哪几拍（`beats: [起, 止]`），
每个节拍必须被恰好一个 cut 认领、按顺序、连续——这让"分镜和剧本"的关系变成**可机械对账**的。

配套 18 道质量门，全部由脚本确定性检查，零依赖、零 API key。

### 3.2 能否吃我们的剧本

能。写了一个约 100 行的转换器，把 `4-2-source.txt`（我们的标准剧本格式）
转成它的 `script.json`（episodes → scenes → flow），`seed` 直接跑通。

### 3.3 两个不兼容的前提

| 前提 | 它的假设 | 我们的实际 | 后果 |
| --- | --- | --- | --- |
| 台词语速 | **4.5 字/秒（中文语速）** | 英文台词 | 休斯一句 92 字符被算成 **17.8 秒**，实际约 5.7 秒 |
| 节拍长度 | 每拍 ≤5 秒 | 有长句节拍 | 装不进单切，必须按句读预拆 |

评估时把语速改成 14 字符/秒（英文）后，同一句变成 5.7 秒，才进入正常范围。

**如果要采用，这两条必须先解决；否则"台词装得下"这道门会驱动错误决策。**

## 四、与稳定链路的质量对比

同样覆盖"亚瑟入场 → 喊话 → 休斯嘲讽 → 亚瑟发怒"：

| | 稳定链路（4-2-stable） | novel-storyboard |
| --- | --- | --- |
| 切分 | 2 个 shot / 3 个 Clip（6+7+5 秒） | **3 段 / 9 切**（3+3+2 / 3+3+3 / 3+2+3） |
| 段内 | 一镜到底，不再切 | **每 2–5 秒一剪** |
| 正反打 | 无 | 有 |
| 构图 | 自然语言 | **6 个量化字段 + 段级 blocking** |
| 台词 | 一句一 Clip | 长句可拆多切 |

**最大差别不是字段，是"镜头内切分"**——这也是短剧节奏的核心。

## 五、为什么不全盘采用

| 原因 | 说明 |
| --- | --- |
| 会重新引入复杂度 | 每切要模型写 6 个字段 + 分镜图提示词，输出量明显大于稳定链路 |
| 它的产物是 skill 不是服务 | 切镜由 agent 按 SKILL.md 做，批量并发要自己搭编排 |
| 交付形态不同 | storyboard.json + 报告 + 投产包，我们的 EOS / 剪映链路要重做 |
| 语速与节拍粒度都要改 | 见 3.3 |

## 八、吸收结果（2026-11-20 落地记录）

### 8.1 blocking 闸门 —— 已实现

`src/blocking.js`，已接入 `StoryboardFlow` 的质检展示（不阻断交付）。

只做两件确定能判的事：

1. 人物表里列出的人，空间位置行里必须有他（否则报 **中**：模型不知道这个人在画面哪里）
2. 称谓不一致（「巴里长老」vs「巴里」）报 **低**，不当作缺失

真实稿复测：

| 场景 | 中 | 低 |
| --- | ---: | ---: |
| 5-1 | 0 | 0 |
| 4-2 | 0 | 0 |
| 8-1 | 0 | 4（称谓不一致：巴里长老/巴里、诺曼伯爵夫人/伯爵夫人） |

合成用例：人物表 3 人、空间位置只写 2 人 → 正确报 1 条中风险。

### 8.2 节拍认领 —— 尝试后放弃

先试了**零提示词改动**的做法：把源剧本拆成节拍，用文本覆盖率反推每个节拍落在哪个分镜。

结果：**噪声太大**。

| 场景 | 节拍 | 假「未认领」 |
| --- | ---: | ---: |
| 5-1 | 30 | 2 |
| 4-2 | 36 | 5 |
| 8-1 | 8 | 2 |

原因是稳定链路的模型会**大幅改写动作描述**（"亚瑟停下脚步，看着前方" → "亚瑟大步走来，停在庭院中央，面朝休斯"），
bigram 覆盖率只有 0.3 左右，和真正漏掉的节拍分不开。

**结论：节拍认领必须由模型显式标注**（像该 skill 的 `beats: [起, 止]` 那样），
从散文反推不可靠。这条如果要上，需要改 `default-storyboard.md` 的输出格式，
属于**契约层改动**，应单独评估，不在本次范围。

**当前不改。** 源块覆盖（`runEngineQc`）继续作为剧情完整性的兜底。
