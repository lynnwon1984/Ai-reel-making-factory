# 成本与速度优化 v0.1

日期：2026-11-05

## 成本结构

使用官方动作规则生成的 62 源块样本：

```text
runs/director-pilot/2026-11-05T08-50-24-947Z/
```

总览：

| 指标 | 数值 |
| --- | ---: |
| 调用次数 | 12 |
| 输入 token | 53,872 |
| 输出 token | 95,729 |
| 总 token | 149,601 |
| 其中推理 token | 76,662 |
| 缓存输入 token | 23,552 |
| 缓存命中率 | 43.7% |
| 累计模型耗时 | 545,594ms |

调用拆分：

| 类型 | 次数 | token | 耗时 | 占比 |
| --- | ---: | ---: | ---: | ---: |
| 导演提示单 | 1 | 6,295 | 9,010ms | 4.2% token |
| 首稿 | 6 | 79,825 | 344,925ms | 53.4% token |
| 定点修复 | 5 | 63,481 | 191,659ms | 42.4% token |

结论：

1. 推理 token 占输出 token 的约 80%。
2. 修复调用占总 token 的 42.4%，是当前最大可优化项之一。
3. 首稿本身也仍然很贵，不能只盯输入 token。

## 已实施：无损输入瘦身

模型输入不再包含重复展示字段：

- `cast` 完整人物行；
- `source` 完整原文镜像；
- 动作微单元里的 `blockId / start / end / source`；
- 冗余运行和展示字段。

模型只收到：

- 集名、场景、`castNames`；
- 导演提示单、场景地理；
- 分块信息；
- 动作块的 `id / text / actionUnits(id,text)`；
- 台词块的 `id / speaker / tone / text`。

效果：

```text
8 个 20 秒分块的模型输入：
旧 35,628 字符
新 27,227 字符
减少 23.6%
```

单场完整 JSON：

```text
30,398 → 16,661 字符
减少 45.2%
```

注意：完整 JSON 不直接全部发给模型，实际节省以分块后的 23.6% 为准。

## 已实施：稳定前缀重排

导演提示单和场景地理移到 JSON 最前，变化内容放后面：

```text

sceneId
episode
sceneHeading
castNames
directorBrief
sceneGeography
chunkIndex
chunkCount

```

当前 8 个分块有约 1,084 字符的稳定公共前缀，占首块约 24.7%。后续可以继续观察缓存命中。

同一个约 20 秒分块：

| 指标 | 瘦身前 | 瘦身后 low | 变化 |
| --- | ---: | ---: | ---: |
| 输入 token | 5,045 | 4,137 | -18.0% |
| 输出 token | 12,237 | 10,936 | -10.6% |
| 推理 token | 10,341 | 9,231 | -10.7% |
| 总 token | 17,282 | 15,073 | -12.8% |
| 耗时 | 65,097ms | 63,605ms | -2.3% |
| shot | 5 | 4 | 仍为合法结构 |

说明：

- 输入瘦身没有破坏 Schema v3；
- 输出长度和推理量也略有下降，但单样本还不能证明稳定比例；
- 时间基本持平，说明耗时主要受推理影响。

## `minimal` 推理档位实验

同一个分块、同样输入：

| 指标 | low | minimal | 变化 |
| --- | ---: | ---: | ---: |
| 输入 token | 4,137 | 4,137 | 0 |
| 缓存输入 | 0 | 3,968 | 第二次调用命中缓存 |
| 输出 token | 10,936 | 8,022 | -26.7% |
| 推理 token | 9,231 | 6,170 | -33.2% |
| 总 token | 15,073 | 12,159 | -19.3% |
| 耗时 | 63,605ms | 45,071ms | -29.1% |
| shot | 4 | 4 | 一致 |
| 高问题 | 动作密度 1 | Clip 内容预算 1 | 都需修复，但类型不同 |

判断：

- `minimal` 有明显降本潜力；
- 输出/推理下降不依赖缓存；
- 总 token 降幅中包含第二次输入缓存命中的收益；
- 目前只有一个分块，不足以改默认档位。

## 尚未启用的优化

### 1. 增大分块

当前按约 20 秒内容预算：

```text
8 个分块
```

如果改成约 30 秒：

```text
5 个分块
```

调用次数能明显减少，但单块推理和输出压力会上升。必须先做质量 A/B，不能直接切换。

30 秒分块：

```text
块数：5
块间源块数：14 / 12 / 14 / 12 / 10
```

### 2. 减少修复调用

当前 5 / 12 次是修复。

下一阶段优先做：

- 首稿前把确定性规则写得更显式；
- 只把失败 shot 返回模型，不重发整块；
- 同一分块最多修复 1 次，仍失败则拆到局部重试；
- 对时长、别名和宽景对白继续由本地确定性修复，不占用模型修复。

### 3. 拆分修复输入

当前修复会重新发送：

- 原始分块；
- 上一版完整 JSON；
- 问题列表。

下一版应尝试：

- 只发问题 shot；
- 保留字段骨架；
- 让模型只返回需要替换的 shot 数组。

目标：降低修复输入和输出长度，同时减少整块重写导致的漂移。

## 当前判断

可以确认：

- 输入瘦身是安全的；
- 稳定前缀重排是安全的；
- `minimal` 有显著潜力；
- 修复调用是最值得继续压缩的部分；
- 增大分块是减少调用次数的最直接办法，但质量风险最高。

下一步应做：

1. 至少用 3 个不同分块对比 `low` 和 `minimal`；
2. 做“只修复失败 shot”的原型；
3. 再评估 25–30 秒分块。
