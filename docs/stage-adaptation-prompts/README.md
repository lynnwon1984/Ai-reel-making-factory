# 从故事到舞台剧本：提示词系统 v1

这套提示词面向 7B–14B 级本地模型。核心不是写一条“长篇万能提示词”，而是把改编拆成可检查的工序：先锁定故事事实，再设计舞台方案，最后逐场写作和验收。

默认目标是一部 90–120 分钟、中文演出、6–10 名演员可兼任的话剧。项目参数可以在 [00-project-config.md](./00-project-config.md) 中改。如果要做音乐剧、儿童剧、沉浸式剧场或戏曲，先改演出形态参数，再运行流程。

## 为什么分成九步

小模型一次完成整部戏，常见结果是：前两场细、后面跑剧情、人物声音趋同、把小说叙述改写成“人物轮流解释剧情”，并且越改越偏。分步调用把每轮任务压成一个明确问题，同时把已经确认的设定固定成后续调用的前缀。

| 调用 | 文件 | 输入 | 输出 | 什么时候停 |
| --- | --- | --- | --- | --- |
| 0 | `00-project-config.md` | 制作条件 | 项目参数 | 参数未知时标 `[待确认]`，不得猜 |
| 1 | `02-source-map.md` | 原文 2000–4000 字一批 | 事实账本 JSONL | 原文全部有 `S###` 编号才继续 |
| 2 | `03-story-bible.md` | 项目参数 + 全部事实账本 | 故事圣经 | 改编取舍和演员兼任方案明确才继续 |
| 3 | `04-scene-plan.md` | 故事圣经 + 事实账本 | 分幕场景卡 | 每场都有可见变化才继续 |
| 4 | `05-scene-draft.md` | 前缀 + 相邻摘要 + 场景卡 + 对应原文 | 单场剧本 | 一景一调用，不生成全剧 |
| 4b | `05b-scene-expand.md` | 过短但事实正确的单场 + 事实账本 | 同剧情扩写场 | 只补调度，不补新事实 |
| 5 | `06-dialogue-pass.md` | 单场初稿 + 人物声音卡 | 对白修订场 | 事件、顺序、进出场不变 |
| 6 | `07-stage-pass.md` | 对白修订场 + 场景卡 | 舞台可演修订场 | 无镜头语言、无舞台事故 |
| 7 | `08-qc-audit.md` | 场景卡 + 原文 + 定稿场 | 质检问题表 | 有问题就进入定点返修 |
| 8 | `09-targeted-repair.md` | 定稿场 + 问题表 | 修补版单场 | 修补后重新跑第 7 步 |

第 0 步是配置，不调用模型。最后的“拼成整本剧本”也应由程序完成，不要让模型重抄全剧。

## 每次调用怎样拼上下文

所有模型调用都先放 [01-base-prompt.md](./01-base-prompt.md)，再接本轮提示词。写单场时，使用下面的顺序，顺序不要变：

```text
[BASE]
01-base-prompt.md 全文

[PROJECT]
00-project-config.md 中已确认的参数

[STORY BIBLE]
第 2 步的最终版，只保留剧作观、人物弧、空间规则、声音卡、兼任表

[PREVIOUS 2 SCENES]
前两场的“已发生事件 + 离场状态”，不要塞完整场次

[CURRENT SCENE CARD]
当前场景卡

[SOURCE]
当前场对应的 S### 原文摘录

[CURRENT TASK]
05-scene-draft.md 全文
```

前缀 `[BASE]`、`[PROJECT]` 和 `[STORY BIBLE]` 在整轮制作中保持不变，能提高本地推理的缓存命中率，也减少设定漂移。场景卡和原文只换当前部分。

## 推荐的本地推理参数

| 环节 | temperature | top_p | 说明 |
| --- | --- | --- | --- |
| 事实账本、故事圣经、场景卡 | 0.15–0.25 | 0.85 | 宁可保守，事实不能发散 |
| 初稿 | 0.35–0.5 | 0.9 | 保留一点语言活性 |
| 对白、舞台修订、定点返修 | 0.15–0.25 | 0.85 | 只改被指派的内容 |
| 质检 | 0.0–0.15 | 0.8 | 需要可重复的判定 |

单场初稿建议限制在 1200–2400 个中文字符。场次更长就拆成 `S07A` / `S07B` 两个调度单元，但戏剧事件仍然只有一个主转折。不要让模型在单次调用里生成三场以上。

## 四个硬门槛

1. **事实门槛**：原文事实、舞台实现、改编取舍分开记录。模型不得把推断写成事实。
2. **变化门槛**：每场结束时，权力、关系、认知、危险或行动方向至少有一项发生变化。没有变化就合并或删除。
3. **可演门槛**：舞台指示必须能由演员、导演、舞监执行。禁止在剧本正文写镜头、剪辑、景别、蒙太奇和影视式画外旁白。舞台旁白或歌队只有在项目参数允许、且故事圣经已规定时才可使用。
4. **证据门槛**：质检只报告能引用原文或成稿的具体问题，不接受“整体不错”“冲突较弱”这类无法返修的评语。

## 改编变更分级

- `T1 媒介翻译`：把叙述、心理和背景转成台词、动作、道具、空间或声音。默认允许，但不能新增关键事实。
- `T2 压缩合并`：删去重复信息、合并相似人物或相邻场景。必须写入故事圣经的变更账。
- `T3 结构重排`：调整时序、地点、视角或角色功能。必须获得项目参数授权并写入变更账。
- `T4 故事改写`：改变事件因果、人物关系、人物结局或主题判断。默认禁止。

“舞台化”不等于“重写故事”。新增一个递水动作可以属于 `T1`；新增一段情史、一次谋杀或一个原故事没有的证人，属于 `T4`。

## 验收方法

每次只验收刚完成的工序，不要等整本写完：

- 事实账本：是否每个原文段落都落到 `S###`？保留的台词是否逐字一致？
- 故事圣经：主角是否有“表面目标 / 深层需要 / 阻力 / 代价”？每个重要改动是否有来源和理由？
- 场景卡：是否有场次结束后什么都没变？是否有角色莫名出现或消失？
- 单场初稿：是否出现镜头语言？是否让人物用对白互相介绍彼此已经知道的事？
- 对白修订：是否有人物声音趋同？是否用解释代替行动？
- 舞台修订：演员能否实际进出？道具是否跟得上？兼任演员是否同时被要求出现在两个位置？
- 质检：`P0` 问题必须归零；`P1` 原则上返修，如导演明确选择保留，必须逐条记录处理决定后才能带入排练稿。

可用 [examples/smoke-test-story.md](./examples/smoke-test-story.md) 做最小跑通测试。它专门放了叙述、内心独白、跨空间、关键道具和未解释信息等改编陷阱。

本机 LM Studio 已启动时，可以直接运行事实账本冒烟测试：

```bash
node scripts/stage-prompt-smoke.mjs
```

默认请求 `http://127.0.0.1:1235/v1/chat/completions` 和 `qwen2.5-14b-instruct-abliterated`，可通过 `LOCAL_API_BASE`、`LOCAL_MODEL` 覆盖。脚本会先把原始请求和完整响应写入 `runs/stage-prompt-smoke/`，再检查 JSONL 字段、连续编号、`change`、逐字引语、字段说明污染和 `SOURCE_INDEX` 完整性。

后续阶段按需运行：

```bash
node scripts/stage-pipeline-smoke.mjs bible
node scripts/stage-pipeline-smoke.mjs scene-plan
node scripts/stage-pipeline-smoke.mjs scene-draft
node scripts/stage-pipeline-smoke.mjs scene-repair
node scripts/stage-assemble-smoke.mjs
```

原始响应和可读正文写入 `runs/stage-pipeline-smoke/`。流水线会优先读取人工批准的事实账本 `source-map-normalized.json`，再按文件修改时间选择最新的圣经和场景卡，避免旧版本被文件名字典序误选。

`scene-draft` 和 `scene-repair` 可追加场次号，例如 `node scripts/stage-pipeline-smoke.mjs scene-draft S02`。拼装器只接受 `scene-S01-approved.md` 这类人工批准文件，并再次运行单场守卫后才生成围读稿。

当前确定性守卫：

- `stage-prompt-guard.mjs`：事实字段、逐字对白、漏句、单字漂移恢复。
- `stage-bible-guard.mjs`：占位符、兼任冲突、原文引语、幕终变化。
- `stage-scene-plan-guard.mjs`：时长预算、累计道具、进出场、字段完整。
- `stage-scene-guard.mjs`：单场汉字预算、实际对白、原文覆盖、模板残留、镜头词、重复段落和下一场越界。

模型输出始终先保存，再经过守卫；守卫失败时进入批准/返修，不得静默接受。

## 产物和版本

每次制作至少保存以下内容，后续返修只替换对应版本：

```text
project-<项目名>/
  00-config.md
  01-source-map.jsonl
  02-story-bible-v1.md
  03-scene-plan-v1.md
  04-scenes/S01-v1.md
  04-scenes/S01-v2.md
  05-qc/S01-qc-v1.md
  06-rehearsal-draft.md
```

每次模型调用还要在解析前保存原始请求和完整响应，至少包含：模型名、量化版本、提示词文件版本、温度、完整输入、原始输出、时间和调用状态。项目现有的 `writeArtifact()` 已采用这一原则；本地模型接入也应复用同样的落盘流程。不要只保存清洗后的 JSON 或剧本。

事实账本、故事圣经和场景卡是“制作合同”。如果临时改了其中任何一项，后续所有相关场次都要重新质检。版本号只增不改，便于比较模型漂移和人工修改。

## 这套提示词不替你做什么

- 不替代版权判断、内容分级和事实核查。
- 不声称模型能准确估算演出时长；分钟数只是排练前的规划值。
- 不让模型决定最终艺术取舍。`T2` 以上变更应交给编剧或导演确认。
- 不负责最终排版和舞台技术图；整本拼装、场次编号、角色兼任冲突和台词计数应由确定性程序完成。
